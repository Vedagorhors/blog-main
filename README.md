# React + Vite

Смотрим план работы и расписываем что и как у нас будет реализовываться.
Согласно пункта 4 плана работ необходимо расписать структуру данных приложения. Итак начнем.

Области хранения данных:

- база данных на json-server
- BFF (backend for frontend - это посредник между сервером и клиентом, но также по хорошему должен находиться на сервере)
- redux store (стор на клиенте, в котором будет храниться состояние приложения)

Сущности приложения:

- пользователь: БД (База данных - список пользователей), в BFF также будет храниться пользователь (сессия текущего пользователя), в redux store также будут храниться данные о пользователе, для того, чтобы отображать в браузере (отображение в браузере)
- роль пользователя: БД (список ролей), BFF (сессия пользователя с ролью), redux store (использование роли пользователя в браузере, точнее использование роли на клиенте)
- статья (сайт будет состоять из статей): БД (список статей), на BFF статьи не нужны, redux store (для отображения данных о статьях в браузере)
- комментарий (к статьям будем возможность писать комментарии): храниться комментарии будут также в БД (список комментариев), на BFF хранить комментарии не нужно, так как для сессии пользователя комментарий не нужен; redux store (хранение комментариев в сторе, потому что нам нужно отображать в браузере, точнее на клиенте)
  Из этих 4-х сущностей строиться всё приложение, весь функционал.

    Таблицы БД:
    - пользователи - users: id / login / password / registed_at (дата регистрации тогда-то (at)) / role_id (id роли пользователя)
    - роли - roles: id / name
    - статьи - posts: id / title / image_url / content / published_at (опубликована статья тогда-то (at))
    - комментарии - comments: id / author_id (он такой же как и id пользователя) / post_id (каждый комментарий должен принадлежать не только какому-то пользователю, но и еще какой-то статье, потому что комментарии отображаются внутри статьи) / content (содержимое комментария) / published_at (дата публикации)
      Возможно будут еще какие-то таблицы, заранее всё трудно предусмотреть, поэтому это нормальная практика

    Схема состояния на BFF (под схемой понимается перечень данных, которые мы там должны хранить. То есть это приблизительная схема, по которой мы будем организовывать наши данные в приложении):

- сессия текущего пользователя: login / password / role

Схема для redux store (на клиенте). Разобъем редакс стор на несколько стейтов:

- user: id / login / roleId / session (на клиенте нужно будет отображать информацию о текущем пользователе, соответственно данные о нем будут храниться в его стэйте под названием user). Пароль нужен только при авторизации. Он отправиться на BFF, а BFF сравнит его с базой данных и потом вернёт ответ авторизован пользователь или нет и также сообщит его роль, вот роль roleId нам уже нужна.
- posts: массив post: id / title / imageUrl / publishedAt / commentsCount (список статей, которые мы будем видеть на главной странице). Posts это массив статей, а статья post должна содержать заголовок title. Еще нужно количество комментариев для каждой статьи - commentsCount

Примечание - в базе данных поля принято принимать через нижнее подчеркивание (published_at), а на клиенте используется camal-case (publishedAt)

- post: id / title / imageUrl / content / publishedAt / comments: массив comment: id / author / content (содержимое комментария) / publishedAt. (сама статья, то есть когда мы открываем на сайте конкретную статью). Комментарии это тоже в свою очередь массив, где один элемент это один комментарий.
- users: массив user: id / login / registeredAt / role (список пользователей, которым будет управлять администратор. Сипсок это тоже массив из пользователей user)
